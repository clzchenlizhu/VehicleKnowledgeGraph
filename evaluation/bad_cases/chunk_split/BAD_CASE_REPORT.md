# Bad Case 分析与切块策略对比报告

> 数据基线：31 题（仅取两集合都有的文档：万用表RS-12、HAK180）。
> Recall@10 语义=96.77% / 固定=96.77%（**持平**）；MRR 语义=82.90% / 固定=67.15%（**语义 +15.75pp**）。
> 切块分布：kb_chunks 89 块、均 162 字、47% <150 字；collection_fixed 49 块、均 470 字、仅 6% 小块。

## 整体结论（一句话）
两边都能把答案捞进 Top10（召回持平），差距全在排序：语义切块靠标题把正确答案顶到 rank=1/2，固定切块把答案压到 5~8 甚至漏掉；但语义切块存在"编号列表被打散"的缺陷，需修。

## 二、共性问题归纳（4 类）

### A. 编号/项目符号列表被切块打散（最严重，直接漏召）
- 涉及：q19（语义漏）、q36（固定漏）、q29。
- 表现：安全手册"1~7 条"、电源线"• 列表"被切到多个碎块，答案句落在不相邻块里，排到 5~8 或直接不进 Top10。
- 本质：**切分只看字符数/标题，不看列表项的语义完整性**。

### B. 标题词命中目录块，正文数值答案被压后
- 涉及：q06、q22、q08。
- 表现：查询词（液晶显示/二极管/电池）先命中"控制与端口""操作步骤"等目录/相邻块，真正含数值答案（2000 位、400~700mV、BAT 符号）的块被压到 5~8。
- 本质：**块自带标题时语义强（语义块 rank=1/2），无标题的固定混合块就弱**。

### C. 近义/重复表述互相稀释
- 涉及：q18、q08。
- 表现：同一手册多块重复"电容放电/断开电源""更换电池"，向量接近，精确答案被相似块挤到 4~5。
- 本质：**与切分策略无关，是知识库重复入库 + 一级排序粒度问题**。

### D. 表格 HTML / 图片链接噪声稀释
- 涉及：q06、q22。
- 表现：`<table>`、`<img>`、长 URL 进块后稀释正文向量，数值短语不突出。
- 本质：**入库前未做文本清洗**。

## 三、全局优化方案

| # | 优化手段 | 对应问题 | 预期收益 | 成本/难度 |
|---|---|---|---|---|
| 1 | **列表原子性切分**：编号列表/项目符号串不跨块切，只在列表项边界切；短列表适当提高单块上限 | A（q19/q36/q29） | 消除两类漏召，Recall@10 96.77%→≈100%；MRR 再 +5~8pp | 低（改 node_document_split 的切分规则） |
| 2 | **标题上下文注入**：每个块正文前拼接所属章节标题路径（如"安全手册 > 电池安装"） | B | 标题词类题从 5~8 拉到 1~3，MRR 显著提升 | 低 |
| 3 | **入库前清洗**：剥离 `<table>/<img>` 与长 URL，保留可读正文 | D | 减少噪声向量，数值短语更突出 | 低 |
| 4 | **近义块去重/合并**：对"安全注意/警告"类重复表述合并 | C | 缓解 q18 类互相稀释 | 中（需相似度阈值 + 合并逻辑） |
| 5 | **检索侧 rerank**：保留一级混合检索，二级加重排（项目已有重排节点），对精确短语加权 | B/C | 直接抬 MRR，不动切块也能见效 | 中 |

### 最终分片策略选型建议
**选语义切块（当前 kb_chunks），但必须修"列表打散"缺陷。**
- 理由：Recall@10 两边持平（96.77%），但真正喂给下游 LLM 的是 Top1~Top5，**MRR 语义 82.9% vs 固定 67.2%，语义 +15.75pp**；固定切块还在 q36 这类题上直接漏召。
- 固定长度切块唯一的"赢"是 q19（因为它把编号列表整块保留了）——这恰好印证了优化点 1：**语义切块只要补上列表原子性，就能把 q19 的漏召也收回来，同时保留所有标题类优势**。
- 结论：语义切块做底座 + 列表原子性 + 标题注入，预期 MRR 可从 82.9% 提升到 90%+，Recall 接近 100%。

## 四、迭代验证流程

1. **改切分策略（只动 node_document_split）**
   - 加"列表原子性"规则：连续编号/项目符号不跨块切断；
   - 每个块前置所属章节标题；
   - 入库前清洗表格/图片 HTML。
   - 对照组 collection_fixed 保持不变，作为公平基线。

2. **重建语义库**：重跑正式导入流程，用新规则重建 `kb_chunks`（正式库）。

3. **重跑评测**：
   ```
   .venv\Scripts\python.exe evaluation\scripts\eval_recall.py
   ```
   同一套 `evaluation/test_sets/test.json`，分别测 `kb_chunks` 与 `collection_fixed`。

4. **对比指标**：
   - 看 Recall@10 是否 ≥ 修复前（不下降）；
   - 看 MRR 是否提升（目标 >82.9%）；
   - 重点回归 7 个 Bad Case：q19（语义应命中）、q36（固定/语义都应命中）、q06/q22/q29（固定排名应进前 3）。

5. **判定标准**：Recall 不降 + MRR 提升 + 7 个 Bad Case 中至少 5 个修复，即为有效迭代；若出现超长块导致新的噪声，再回调单块上限。
